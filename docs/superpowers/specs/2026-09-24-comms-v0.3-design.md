## Controlling statement

v0.3 cuts over from a read-only, proof-carrying Telegram gateway to `owner_full_admin`: one MCP surface with typed reads and writes over Telegram (bot and user) and WhatsApp (the Cloud API and webhooks), under one anchored comms audit chain.

- **Old evidence stays verifiable, but it no longer authorizes anything new.**
- **Every real provider side effect enters an already-finished durability and audit substrate.** Part B precedes Part C for this reason.

## 0. Decisions

See the spec, D1–D5. In short, there is one plan, one branch and one merge; the snapshot is committed with a keyed HMAC; all three provider accounts will be available; `comms mcp` is the only AI surface; and `owner_full_admin` applies exactly as P defines it.

## Part A: the constitutional cutover

**A.1 Scope.** Part A implements A1–A6, A33 (the `tgml1` retirement) and the tombstones. It ships no new provider behaviour.

**A.2 The spec checkpoint.**
- `docs/comms-spec-v0.3.md` and `docs/comms-v0.3-supersession.json` are committed.
- `tests/security/test_supersession.py` checks the manifest against three things: the tombstone multiset, production composition (no retired surface is registered or reachable), and the spec's tombstone list.

**A.3 Retiring the surfaces.**
- The Telegram MCP server's `server.py`, `dispatch.py`, `sensitive_dispatch.py`, the demo server and the disclosure-on-read wiring are removed from production composition.
- Code that only historical verification needs is kept behind a verification-only module whose imports are guarded (A3).
- WhatsVault's `apps/mcp` is removed from the tree. It was never part of the installed distribution (5b-3 R3), so what's left is only an accounting entry.
- `telegram-mcp serve` refuses with a fixed message.

**A.4 The tombstones** are the 16 tool names, `tgml1`, `tg-mcp-policy-bundle/v1` and `tg-mcp-policy-signature/v1`. The legacy audit domains are *closed to new appends*, not tombstoned, because verification still uses them. `test_tombstones.py` counts each by name.

**A.5 The chain engine goes to core**, per M5. It is built this way:
1. Characterization vectors are captured from the legacy chain at `c830d3f`: every MAC, genesis value and checkpoint, byte for byte.
2. `comms.core.audit.chain` is written as a parameterised engine with profiles `LEGACY_TELEGRAM` (the existing domains) and `COMMS` (`comms-audit-chain/v1\0`, genesis `comms-audit-genesis/v1\0`).
3. Transactions go through the single `write_tx`. The engine keeps no private copy.
4. The legacy verifier must reproduce every vector.
5. The legacy module becomes a thin import of the core engine and its profile.

The anchor moves the same way, gaining `comms/audit-head-anchor`.

**A.6 `comms.db` schema v2** is an append-only migration adding:
- `audit_events` and `audit_checkpoints`, with the same row shapes as the legacy chain (§12.2 columns);
- `audit_anchor_state`;
- `audit_lineage`;
- `cutover_state` (`cut_` ref, phase, digests);
- `campaign_events.event_digest` (A16).

**A.7 The cutover command.** `comms cutover run` is operator-only (A37). It implements A6's protocol as a resumable state machine: `NONE → CUTOVER_ENTERED → LEGACY_DRAINED → LEGACY_VERIFIED → LEGACY_SEALED → LEGACY_ANCHORED → COMMS_GENESIS → COMMS_ANCHORED → LEGACY_CLIENT_AUTH_REVOKED → COMPLETE` (exact next-state table, rev 2). Each phase is persisted before the next one begins.

On resume, a phase whose output already exists for this `cut_` ref is checked and reused. A digest conflict fails closed.

`audit verify --all` reports an integrity failure for:
- a comms genesis whose `audit_lineage` doesn't match the legacy seal;
- a legacy seal with a second, different comms genesis;
- a missing lineage record.

**A.8 The `tgml1` → `cml1` cutover.** At `COMPLETE`, every `tgml1` seed is revoked and the security epoch is bumped. `cml1` seeds are then provisioned by `comms client add`. The two formats never coexist as authority.

**A.9 The Part A exit gate** is the owner's checklist, which the Part A tag test pins in full:

| Group | Checks |
|---|---|
| **Spec** | v0.3 normative; precedence resolved; manifest green |
| **Legacy surface** | none of the 16 names advertised; direct calls to them cause zero effects; `telegram-mcp serve` refused; `apps/mcp` absent |
| **History** | v1/v2 receipts verify; the legacy chain verifies; historical key coverage complete |
| **Cutover** | drained, sealed and anchored; `cut_` durable; genesis bound; `system.audit_cutover` chained and anchored; each crash boundary converges on restart; mismatched lineage fails closed |
| **New surface** | a catalog skeleton exists (`comms_*`, closed dispatch); deterministic; collision-free; annotated honestly; no raw RPC; no secrets |

Test accounting follows the 5b-3 method (`before.txt`, `after.txt`, a classification JSON), with unexpectedly missing = 0.

After the full gate: an annotated local tag `comms-v0.3-part-a`, its SHA recorded in the evidence, and no rebase across it.

## Part B: durability, audit, keys, retention, recovery, backup

**B.1 Epochs and truncation** (Phase-5 §3.8, re-targeted at the core engine).
- `seal_and_open_epoch` and `verify_chain(profile, keys_by_epoch, root=)`.
- Epochs must be contiguous, and each must end at a sealing checkpoint whose signature verifies.
- A truncation root must be the latest verified checkpoint at or before the cutoff (A15).
- The probe becomes a regression test, with five named attacks: a missing middle epoch, a truncated tail, a forged root, a root without its row, and a skipped epoch number.
- All of this is built test-first, before any rotation, purge or import code.

**B.2 The external anchor and degraded mode** (A8).
- The anchor is refreshed after every append.
- The degraded latch is checked at every `PREPARED → IN_FLIGHT` transition, every campaign claim, and the start of every maintenance mutation.
- Completing already-in-flight work bypasses the latch by design.
- **The cost of anchoring every event is measured first.** A batched anchor would be a spec change under A39, never a silent optimisation.

**B.3 Journal-to-chain binding** (A16). `append_event` computes `event_digest = SHA256("comms-campaign-event/v1\0" ‖ canonical payload)`. In the same transaction it appends the chain event `{kind: campaign_event, subject_ref, subject_digest}`. The chain event carries no second copy of the payload.

**B.4 The key inventory** (A9–A11, A38). Every key uses versioned immutable slots and an SQL active pointer, rotated stage → prove → activate.

| Purpose | Kind | Rotation consequence | Old material |
|---|---|---|---|
| `audit-chain-key` | HMAC | seal the epoch and open the next | kept until the epoch is truncated behind a verified root |
| `audit-checkpoint-key` | Ed25519 | new key ID | public half kept through checkpoint retention |
| `campaign-commit-key` (new) | HMAC | new key ID for new commitments | secret kept while commitments under it are retained |
| `backup-key` | Ed25519 | new key ID; the old one becomes `TRUSTED_RETIRED` | compromise sets `VERIFICATION_ONLY` or `REVOKED` (A11) |
| `cursor-key` | HMAC | every cursor and `ctx_` handle invalidated | deleted at once |
| `comms-db-key` | raw 256-bit | the A14 rekey sequence | destroyed after a verified reopen |
| `cml1` client seeds | HMAC | per client (`comms client rotate`) | deleted |
| OAuth signing / refresh / registration material | per scheme | new key ID; tokens reissued | public halves kept through token lifetime |
| Provider credentials (Telegram session, bot token, Meta token, app secret, webhook secret) | opaque | A13 staged activation | secret slot destroyed after the post-activation re-check; provider-side revoke via runbook |
| TLS keys (only if Comms terminates TLS) | per scheme | reissue | deleted |
| `principal-key`, `privacy-key` (retired, HMAC) | HMAC | refused | A10: kept only while a proven dependency exists |
| `disclosure-key`, consent keys (retired signers) | Ed25519 / P-256 | refused | public halves for historical verification only |

**Crash recovery covers every boundary**, with each row a test:
- **Before the pointer switch:** the new slot is an orphan. Doctor reports it, and the next run cleans it up.
- **After the pointer switch:** SQL picks the new version.
- **Rekey (A14):** the file's actual key is found by trial-opening under the pointer's key and then the staged key. A mismatch is resolved toward whichever key verifiably opens the file, and nothing is destroyed until the reopen verifies.

**B.5 The campaign commitment** (A12). `campaign_commitment` and its `campaign_commit_key_id` are computed at freeze and stored on the generation row. They are carried on the `campaign.send_started` and `campaign.scheduled` chain events. Verification recomputes the HMAC from the stored `snapshot_digest`.

**B.6 Telegram user-session lifecycle** (Phase-5 §3.1–3.3, with no Touch ID).
- **`auth revoke-this-session`** runs two transactions. The first sets a `REVOKING` state and bumps the epoch. A single `LogOutRequest` is then sent, never retried, and recorded as `confirmed`, `failed` or `unknown`. The local session is wiped whatever the outcome. A second transaction sets `LOGGED_OUT`. At startup, a leftover `REVOKING` finishes without resending.
- **The error-mapping fix:** `AuthKeyUnregistered`, `SessionRevoked`, `SessionExpired` and `AuthKeyDuplicated` map to `SESSION_REVOKED`. `UserDeactivated*` maps to `ACCOUNT_UNAVAILABLE`. A Telethon `AuthKeyNotFound` maps to `TELEGRAM_UNAVAILABLE`.
- **Recovery** is `auth login`, with `--new-account` handling. The `accounts` table, which projects still reference, keeps its rows for history.

**B.7 Provider credential lifecycle.** `comms credential set|rotate|revoke <purpose>` follows A13. Revoking destroys the secret slot (the daemon's 0600 file store, A13 rev 2) and appends a chain event, and the adapter then reports `NOT_CONFIGURED`.

**B.8 Retention** (A15). One maintenance runner works under the append guard, in foreign-key order:
1. Legacy exposure rows past `exposure_ledger_days`.
2. Legacy receipts past their floor, once their exposure and audit children are gone.
3. Legacy `message_ref` rows.
4. The comms chain prefix, at the root from B.1.
5. Campaign body redaction: `generations.content`, `delivery_jobs.payload` and any render blob of a `COMPLETE` or `CANCELLED` generation past `campaign_body_days`.
6. Directory identities of endpoints disabled for longer than `identity_retention_days`, and never while an unresolved job references them.
7. Retired public keys and secrets that nothing references.
8. A `maintenance.retention_purge` event.

Schema v3 carries three things:
- `redacted_at` columns;
- triggers that allow exactly the redaction update (body to `NULL`, digests kept) and nothing else;
- a relaxation of the 5b-4 payload `CHECK`, so a redacted job may have a `NULL` payload with its digest retained.

**B.9 Backup and import** (A17, Phase-5 §4 re-targeted).
- The age-v1 X25519 subset is vendored with the C2SP testkit vectors and the named negatives.
- Signatures are Ed25519 detached, under `comms-backup-signature/v1`, with golden vectors.
- Ciphertext moves by 32 KiB transfer frames, and the identity is read from a file or stdin only.
- The payload is `comms-backup/v1`. Its account binding is `SHA256("comms-backup-binding/v1\0" ‖ JCS({installation_ref, providers: {telegram_user, telegram_bot, whatsapp_phone}}))`, covering whichever providers are present.
- Import runs: trust check → verify → decrypt → strict decode → binding check → stage the diff against `base_digest` (a `tps_` handle) → commit, which rechecks the base, applies the diff, and calls `seal_and_open_epoch` with `admin.backup_import` as the first event.
- A plaintext-scan test plants every secret from B.4 and every body canary. Directory identities are allowed inside the ciphertext only, and the sidecar, diff output and logs are scanned for them.

**B.10 Doctor and runbooks.**
- **Doctor checks:** key inventory and orphans, historical-key coverage, maintenance overdue, the health of both chains, the lineage, credential presence (metadata only), the degraded latch, and the cutover state.
- **Runbooks:** install, uninstall, restore-from-backup, session-compromise, key-compromise (one section per purpose), audit-degraded, provider-credential-rotation and cutover.
- **A test requires every runbook command to exist** and to have a handler.

Part B ends with a full gate and the tag `comms-v0.3-part-b`.

## Part C: provider adapters

**C.1 Contracts** (A18). Core defines the protocols; transports implement them.

| Protocol | Operations |
|---|---|
| `DeliveryTransport` | The 5b-4 contract, unchanged. |
| `CapabilityProvider` | `snapshot(actor, destination) -> CapabilitySnapshot` |
| `AdminOperations` | `invoke(op: SemanticOperation, target_refs, args, op_key) -> ProviderResult` |
| `ContextSource` | `read(query) -> ContextPage` |
| `InboundSource` | `normalize(raw) -> InboundEvent` |

`ADAPTER_CONTRACTS` declares which protocols each adapter supports. The conformance suite runs every declared contract. Unexplained skips = 0, and an advertised-but-unimplemented contract = 0.

**C.2 `telegram/bot`.**
- **Transport:** the Bot API over `httpx` (M2), to `api.telegram.org` only.
- **Updates:** `getUpdates` long polling (A24), with an offset persisted so every update is processed once.
- **Capability:** from `getChatMember(me)` rights.
- **Classification:** a named-case table (A19).

**C.3 `telegram/user`.**
- **Client:** the existing Telethon adapter and single client (A21), with `request_retries=0` and `flood_sleep_threshold=0` pinned by a test.
- **RPC sets:** `READ_RPCS`, `WRITE_RPCS` and `ADMIN_RPCS` are named by capability, and a runtime recorder proves nothing outside them is sent.
- **Sends:** `random_id` reconciliation (A20).
- **Capability:** basic-group versus supergroup differences are hidden inside the capability provider.
- **Context:** history, search, participants and the admin log, under the Phase-4 bounds.

**C.4 `whatsapp/cloud`.**
- **Transport:** the Graph API over `httpx`, to `graph.facebook.com` only.
- **Surface:** send (text, media by ID, template, interactive, reply), templates (CRUD), media (upload, retrieval through the bounded Meta-URL downloader, delete), account and phone status, and groups only when discovery reports them.
- **Window:** from the mirrored state (A22).
- **Templates:** frozen into the payload (A23).
- **Classification:** a per-code Meta table.

**C.5 `whatsapp/webhooks`.** The A36 ingress:
1. Read bounded raw bytes and check the HMAC in constant time, then parse.
2. Normalize to `InboundEvent`.
3. Ingest into the WhatsVault archive.
4. Mirror `last_customer_message_at`.
5. Feed statuses to `record_provider_update`, where duplicates are harmless and early statuses become `pending_match`.

**C.6 Operation semantics** (A27). The `OperationSemantics` table is keyed by semantic operation and transport:
- **`SET_STATE`** (title, description, exact admin rights, restrictions, ban state, unban) is generally idempotent.
- **`CREATE`** (invite, group, topic) is non-idempotent.
- **`MESSAGE_SEND`** is idempotent over MTProto only.

Conformance tests pin every entry.

**C.7 Egress** (A26). An AST guard allows only the adapter network modules to import `httpx` or `telethon`. A runtime host guard wraps the `httpx` transport and refuses any host outside the adapter's pin. Every adapter has a canary test for tokens, identities and bodies in logs.

**C.8 Oracles.**
- **Meta:** WhatsVault's `fake_meta.py`, extended into a contract oracle covering send, templates, media, statuses, groups discovery and the webhook signature.
- **Bot API:** recorded fixtures.
- **MTProto:** a fake Telethon client at the adapter boundary.

Each fixture records its provider, API or layer version, source reference, capture date and SHA-256. Live mode (`--run-live-acceptance`) runs the same suite against real accounts. Its output is evidence only.

**C.9 Live runbooks** cover P §84–85: disposable Telegram groups for the bot and user tests, and a Meta test number.

Part C ends with a full gate and the tag `comms-v0.3-part-c`.

## Part D: the unified surface

**D.1 The service layer** (A37). Typed services own every read and write: context, capability, group admin, messages, campaigns (5b-4), directory, templates, media, account, and the operator-only services. MCP, the CLI and maintenance are thin ingresses over it.

**D.2 Operation records** (A27, A28, §E.2).
- **Schema v4:** `admin_operations(op_ref, authenticated_client, request_id, request_digest, tool, target_refs, actor, semantics, state, provider_outcome, audit_status, …)`, with `UNIQUE(authenticated_client, request_id)`.
- **Lifecycle:** `PREPARED → IN_FLIGHT` (chained and anchored) → provider call → `SUCCEEDED | FAILED | OUTCOME_UNKNOWN`, with an independent `audit_status` of `ANCHORED` or `DEGRADED`.
- **Retry:** follows the semantics table.
- **Exceptions:** become `OUTCOME_UNKNOWN` only at the provider-call boundary, as in the 5b-4 engine.

**D.3 The context engine.**
- **Operations:** P §19–22.
- **Provenance:** every item carries one of `telegram_live`, `telegram_local`, `whatsapp_webhook_archive` or `campaign_store`.
- **Bounds:** P §71's search limits.
- **Handles:** `ctx_` handles (A30) are stored server-side, with digest, client, epoch and expiry.
- **Untrusted content:** it goes into explicitly untrusted fields, and no write accepts it (A32).

**D.4 Refs** (A31). New core prefixes are `grp_ msg_ inv_ tpl_ top_ med_ ctx_ op_ req_ cut_ cli_`, held to the disjointness test. `grp_` maps 1:1 to a group `dst_` (`UNIQUE`). Resolution tools return `AMBIGUOUS_TARGET` when more than one target plausibly matches.

**D.5 The catalog** (A29).
- **One source:** `TOOL_CATALOG` holds P §22–35 plus `comms_admin_identity_inspect`. Every tool has input and output schemas, annotations and a failure-mode list.
- **Generated from it:** `tools/list`, dispatch and the documentation table.
- **Pinned:** the catalog count, order, per-tool schema digests and the overall digest.

**D.6 `comms mcp`.**
- **stdio proxy** (A34): enforced by an AST guard that the proxy imports no keys, storage, adapters or Telethon.
- **Streamable HTTP `/mcp`:** authenticated with `cml1` locally (A33) and OAuth remotely (A35).
- **Behaviour:** stateless per MCP `2026-07-28` (M1), with a closed allowlist.

**D.7 The CLI.** The `comms` command groups are campaign, location, audience, group, message, template, transport, credential, keys, audit, retention, backup, doctor, cutover and client. Operator-only commands are never MCP tools. The CLI generates and prints the `req_` and `op_` refs.

**D.8 Ingress** (A36). `comms-mcp-tunnel` and `comms-webhook-tunnel` are separate listeners. A test proves that a webhook-route request cannot reach MCP dispatch, and the reverse.

**D.9 Remote OAuth** is built **last**, because Claude Code and Codex work without it. It provides the metadata endpoints, PKCE `S256`, token validation per A35, and a single owner subject.

**D.10 The smoke test moves over.**
- **What it drives:** `comms mcp` over real stdio and HTTP, the real CLI and the real admin socket, against fake adapters.
- **Accounting:** each of the 52 legacy checks is retained, replaced or retired with a reason, with unexpectedly missing = 0.
- **New checks:** writes, campaigns, admin operations, OAuth, context, WhatsApp and capability.

**D.11 Client runbooks** for Claude Code (`.mcp.json`, `allowedTools: ["mcp__comms"]`), Codex, and ChatGPT (plugin, tunnel, OAuth). Each run records the client and version, the negotiated protocol, the catalog digest, the auth mechanism, the visible tools, and a read, a write, a destructive call, an ambiguity refusal and a request-id replay.

Part D ends with a full gate and the tag `comms-v0.3-part-d`. Then comes the single merge, with owner approval.

## E. Proof

**E.1 The gate.** The existing full gate (contracts, pytest, smoke, formal, ruff, format, mypy, build and the WhatsVault suite) must be green before every commit.

**E.2 Formal models.** Each property is mutation-tested, and each model has a differential walk against the library.

- **The campaign model** (5b-4) is kept.
- **The admin-operation model.** For one operation identity `(authenticated_client, request_id)`, any number of MCP retries, duplicate calls, reconnects and restarts produces **at most one non-idempotent provider effect**. The other properties:
  - a normal `SUCCEEDED` response implies a durable outcome, a chain append and an anchor;
  - `provider_outcome = SUCCEEDED` with `audit_status = DEGRADED` returns `op_`, the known outcome and `AUDIT_INTEGRITY_DEGRADED`, never ordinary success;
  - while degraded, no new `PREPARED → IN_FLIGHT`, no new claim and no new maintenance mutation, while the completion of already-in-flight work stays reachable;
  - MTProto reconciliation issues at most one extra RPC with the identical `random_id`, produces at most one visible effect, and ends as `ACCEPTED` or `OUTCOME_UNKNOWN`.

  Cross-client semantic duplicates are not modelled and not claimed.
- **The audit-chain model:** epochs are contiguous and each sealed; truncation is only at a verified root at or before the cutoff; nothing is appended after `SEALED`; and the lineage legacy seal ↔ genesis ↔ `audit_lineage` holds or fails closed.
- **The key and credential model:** across every crash boundary of staged rotation and rekey, the active pointer and the key that actually opens the database never diverge unrecoverably, and a failed candidate never displaces a working credential.

**E.3 Structural suites.**
- **Catalog:** the canonical `TOOL_CATALOG` serialization is byte-identical; the ordered semantic `tools/list` payload is structurally identical, ignoring JSON-RPC framing; and the schema digests and overall digest are stable.
- **Dispatch:** closed. Direct calls to the 16 retired names cause zero effects, and no write accepts `ctx_` or text.
- **Honesty:** annotations are honest, and no raw-RPC tool exists.
- **Privilege boundaries:** the proxy imports nothing privileged; only adapter network modules import network clients; there is a single Telethon importer, whose `request_retries=0` and `flood_sleep_threshold=0` are pinned; and webhook ingress is isolated from `/mcp`.
- **Constitution:** tombstones, the manifest, and test accounting.
- **Privacy canaries** over every MCP result, stdio and HTTP frames, CLI output, logs, webhook responses, backup metadata, and every file in every database directory.

**E.4 Adapter conformance.** One suite runs over `ADAPTER_CONTRACTS`. It covers the classification tables, operation semantics, capability states, rate-limit normalisation, the 24-hour window, template freezing, and a separate conformance family for webhook signatures and idempotence. It runs on fakes in the gate and live only as evidence.

**E.5 Crash tables, one test per row:**
- the cutover phases (A.7);
- every rotation and rekey boundary (B.4);
- the retention phases;
- the admin-operation lifecycle;
- webhook ingestion;
- anchor failure after a provider outcome.

**E.6 What CI does not prove.** Ambiguity refusal, request-id replay and schema quality are deterministic, so they sit in the gate. Model tool *selection* (P §80) is owner-run acceptance evidence and is never presented as a proven property.

**E.7 Evidence.**
- `docs/verification/comms-v0.3.md` has one section per part: the tags and SHAs; the catalog digest and tool inventory; the capability inventory and known unsupported capabilities; provider API and layer versions and the MCP version; the counts; canary results; `audit verify --all`; the P §88 table as owner-run evidence; and the D5 claim boundary, verbatim.
- `docs/verification/comms-v0.3-rulings.md` gives each ruling an ID, date, the affected section, the discovery, the decision, the reason, the affected tests and the commit SHA (A39).

**E.8 Release.** Merging follows D1. The release designation follows A40.

## F. Size and risks

- **Size:** about 130 tasks, in four parts.
- **Compaction:** the execution ledger and the rulings file carry state across compaction, and every task brief is self-contained.
- **The biggest technical risks, each measured before its task depends on it:**
  - the cost of per-event anchoring (B.2);
  - `PRAGMA rekey` behaviour under SQLCipher 4.12 (B.4);
  - Bot API and Meta fixture fidelity (C.8);
  - the MCP SDK's stateless HTTP and OAuth hooks (D.6, D.9).

## G. Out of scope

- Narrower profiles (P §7.2).
- MCP Apps UI (P §63).
- SMS and email transports.
- Unofficial WhatsApp Web automation, which is forbidden by P §13.
- Phase 6/7 installed-client and release gauntlets beyond P §88.
- The GitHub rename, the whatsvault archive and the folder move, each a separately approved operational step.
