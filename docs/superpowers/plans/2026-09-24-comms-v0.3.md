# Comms v0.3 Implementation Plan: Parts A–D (5c + 5d + 5e)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Execution method, chosen by the owner:** inline (`superpowers:executing-plans`). No subagents. Test-first, with a fail-fast full gate before every commit.

**Goal:** Replace the read-only Telegram MCP with `comms mcp`: a single stateless MCP surface giving the connected host `owner_full_admin` authority over typed reads and writes on Telegram (bot and user) and WhatsApp (Cloud API and webhooks). Every side effect goes through durable operation records and one anchored comms audit chain, cut over provably from the legacy chain.

**Architecture:** Four parts on one branch (`comms-v0.3`), each ending in a green gate and an annotated local tag.

| Part | Scope |
|---|---|
| **A** | The constitutional cutover: retire and tombstone the old surfaces; move the chain engine into core; seal the legacy chain; write the comms genesis. |
| **B** | Durability: epochs, the anchor, keys, rotation, retention, recovery, backup. |
| **C** | Provider adapters behind core protocols, proven by fakes and oracles. |
| **D** | The service layer, operation records, context engine, the `TOOL_CATALOG` MCP surface, stdio proxy, CLI and OAuth. |

**Tech Stack:** Python 3.12, `sqlcipher3` 0.6.2 (SQLCipher 4.12.0), stdlib `sqlite3` (the legacy Telegram DB), `mcp` 2.2.0, `telethon` 1.45.0, and `httpx` 0.28.1, promoted to a runtime dependency in Task C1 (M2). Tooling: pytest, ruff, mypy.

**Spec:** [`docs/comms-spec-v0.3.md`](../../comms-spec-v0.3.md) (normative; A1–A40 win over P) and [`docs/superpowers/specs/2026-09-24-comms-v0.3-design.md`](../specs/2026-09-24-comms-v0.3-design.md) rev 1 (committed at `92211a9`). "§A.n" refers to the design, "An" to a spec amendment, and "P §n" to the owner's proposal.

**Branch:** `comms-v0.3`, from `main` at `c830d3f`.

**How to read a task.** Each task names its files and interfaces, lists the failing tests it must write first (each by name and the exact behaviour asserted), then gives the implementation specification with the code or SQL wherever the shape isn't obvious, and ends with its commit message. ## Global Constraints

- **The spec wins (A39).** A contradiction between the plan and the spec stops the task; the spec stays authoritative, and the plan or spec is amended explicitly. The ruling is recorded in `docs/verification/comms-v0.3-rulings.md` (ID, date, section, discovery, decision, reason, tests, SHA) and in the ledger, and the affected gate is rerun.
- **One daemon owns privilege (A34).** Only the daemon process opens `comms.db`, holds keys or credentials, runs Telethon or calls providers. The stdio proxy, the CLI and tests of either reach it through authenticated local IPC.
- **No external I/O inside a `comms.db` transaction** (5b-4 R18). `prepare`, `still_valid`, `normalize`, `CapabilityProvider.snapshot` from cache and anchor *computation* are pure. Provider calls, anchor file writes and Keychain access happen with no transaction open, guarded by `io_guard`.
- **The exception boundary.** Only an exception raised by a provider call becomes `OUTCOME_UNKNOWN`. Everything else propagates and fails closed.
- **One copy of each rule.** One JCS, one opaque minter, one `write_tx`, one chain engine, one anchor engine, one `TOOL_CATALOG`, one `OperationSemantics` table, one strict JSON decoder.
- **Opaque refs outside the database.** No MCP result, CLI output, log, exception, event or backup metadata carries a phone number, raw Telegram ID, Meta ID, token or body, except `comms_admin_identity_inspect` (P §44) and data inside encrypted storage or backup ciphertext.
- **Core never imports a transport** (M3 guards). Adapters implement core protocols.
- **Tombstones are permanent.** No retired identifier is reassigned (v0.2, A2).
- **Degraded mode (A8).** While `audit_integrity_degraded` is set, there is no new `PREPARED → IN_FLIGHT`, no campaign claim, and no retention, import or rotation mutation. Completing and recovering already-in-flight work stays allowed.
- **Idempotency.** Every mutating MCP tool requires `request_id` (A28). A non-idempotent operation is never retried after ambiguity (A27).
- **Egress (A26).** The Bot API goes only to `https://api.telegram.org`, the Graph API only to `https://graph.facebook.com`, media only through the bounded Meta-URL downloader, and MTProto sockets only through Telethon's own machinery.
- **The automatic gate never touches a network or real account.** Live acceptance runs only under `--run-live-acceptance`, and its results are evidence only (A40).
- **The full gate:** `scratchpad/fullgate.sh`: `uv sync --locked`, contracts, `pytest`, smoke, formal, ruff, format, `mypy src/comms src/telegram_mcp`, build, plus the WhatsVault suite. **Commit only on `GATE ok=1`.**
- **Read `AGENT.md` and `CHANGELOG.md` before editing, and append a dated `**Raouf:**` entry to each** at every part's end (Tasks A23, B33, C34, D38).
- **Checkpoints.** Tag each part with an annotated local tag (`comms-v0.3-part-a` … `-d`). A checkpoint commit is never rebased. Pushing tags needs owner approval.
- **Never commit or log** credentials, session material, keys or private content.

## Review Focus

1. **A crash between "provider may have acted" and "outcome recorded", for an admin write rather than a campaign.** The user expects no duplicate effect and an honest `OUTCOME_UNKNOWN` carrying the `op_` ref. *Tests: Task D5's crash table, and Task D35's admin-operation model.*
2. **An LLM retries a mutating tool with the same `request_id` after a timeout, or reuses the ID for different arguments.** The user expects the existing operation back, or `REQUEST_ID_REUSE`. *Test: Task D4, `test_request_id_replay_returns_the_existing_operation` and `test_request_id_reuse_with_new_arguments_is_refused`.*
3. **Anchor refresh fails after a provider success.** The user expects `AUDIT_INTEGRITY_DEGRADED` with the known outcome, never plain success or failure, and further writes blocked. *Test: Task D5, `test_anchor_failure_after_provider_success_is_degraded_not_success`.*
4. **The cutover crashes midway and is re-run.** The user expects one seal, one genesis, the same `cut_` ref, and a fail-closed result on any conflict. *Test: Task A13's cutover crash table.*
5. **A webhook request probes `/mcp`, or an MCP request probes the webhook route.** The user expects no route between them. *Test: Task D34, `test_webhook_listener_has_no_route_to_mcp_dispatch` and its reverse.*

Per phase, in order, with the phase persisted in `cutover_state` before the next begins:

1. **`CUTOVER_ENTERED`:** mint `cut_`.
2. **`LEGACY_DRAINED`:** `barrier.close_ingress()`, then wait for `barrier.drained()`, bounded at 30 s; on timeout, `CutoverError("legacy work did not drain")`.
3. **`LEGACY_VERIFIED`:** `verify_chain(LEGACY_TELEGRAM)` plus `derive_integrity`. Anything other than `ok` raises.
4. **`LEGACY_SEALED`:** in one legacy `write_tx`, append the marker event `{"kind":"system.cutover_final","cutover_ref":…}`, write the checkpoint with `reason="V0_3_CUTOVER"`, and set the legacy settings row `audit_append = sealed`. Then store the `legacy_checkpoint_digest` (SHA-256 of the checkpoint's canonical JSON) in `cutover_state`.
5. **`LEGACY_ANCHORED`:** refresh the legacy anchor.

`cutover_barrier.py` implements the barrier over the Telegram runtime: it sets the lifecycle to refuse legacy MCP ingress, counts in-flight requests down to zero, and makes the legacy `append_event` binding raise `ChainError("legacy chain is sealed")` whenever `audit_append = sealed`.

### Task B12: The `comms-db-key` rekey protocol (A14, N1)

**Files:**

The sequence:
1. Stage the new key as version *n+1* in `SecretStore`.
2. With **no transaction open** (raising `TransactionIOError` otherwise, per N1), `PRAGMA rekey`.

### Task D4: The operation executor

**Files:**
- Create: `src/comms/services/operations.py`.
- Test: `tests/services/test_operations.py`.

**Interface:** `def execute_operation(ctx: CallContext, tool: str, targets: Targets, op: SemanticOperation, request_id: str) -> OperationOutcome`.

The sequence:
1. Compute `request_digest = SHA256(JCS({tool, args, targets}))`.
2. In one `write_tx`: if the `(client, request_id)` row exists, return its outcome when the digest is equal, and raise `REQUEST_ID_REUSE` otherwise. If not, `require_not_degraded`, insert `PREPARED`, then `IN_FLIGHT` with the chain event.
3. Refresh the anchor, with no transaction open. A failure latches degraded and **aborts before the provider call**, leaving the operation `IN_FLIGHT` with `audit_status=DEGRADED`, which recovery marks `FAILED` with `provider_code=NOT_ATTEMPTED`.
4. `io_guard`, then the adapter call. Only its exception becomes `OUTCOME_UNKNOWN`.
5. In a `write_tx`, record the outcome and the chain event.
6. Refresh the anchor. On failure, return `AUDIT_INTEGRITY_DEGRADED` with `op_ref` and the known outcome.

The same `request_id` after `OUTCOME_UNKNOWN` returns the unknown and never re-calls. The operation's `op_key` is `SHA256("comms-admin-op/v1\0" ‖ client ‖ request_id)` (domains, wire test).

  - `test_request_id_reuse_with_new_arguments_is_refused`.
